# CloudAttackLab audit, November 2026

- Date: 2026-11-16
- Commit audited: `47e5d58` (main, "Merge pull request #11 … step-12-real-shopcloud")
- Machine: Windows 11, Docker Engine and Compose inside WSL 2 (Ubuntu), Python 3.14.4 in WSL
- Scope: audit only. No code, configuration or `.env` was changed. Where a test needed a different setting (`SHOPCLOUD_URL`, `TELEMETRY_SOURCE`), it was set in the shell for one `docker compose up -d backend`, and the backend was recreated with the normal settings straight afterwards.

## How the audit was run

1. Pulled `main` (fast-forward to `47e5d58`). Read `README.md`, `docs/api-contract.md`, `docs/shopcloud-interface.md`.
2. Clean state: `docker compose -f lab/docker-compose.lab.yml --profile falco down -v`, `docker compose -f monitoring/docker-compose.monitoring.yml down -v`, `docker compose down -v`. All `cloudattacklab*` containers, networks and the `cloudattacklab_pgdata` volume were removed.
3. Started again using only the README: `.env` already existed (it sets only `TELEMETRY_SOURCE=docker`), so `cp .env.example .env` was skipped to leave it unchanged; then `docker compose up -d --build`. The dashboard was driven in a browser at `http://127.0.0.1:5173`; the API and Docker were checked from the terminal.
4. The monitoring stack was started later with the README command `docker compose -f monitoring/docker-compose.monitoring.yml up -d`.

Evidence below is trimmed command output, API responses, and what the dashboard and Grafana showed.

## Bugs found, most serious first

1. **The lab target URL is not checked, so scenario traffic can leave the lab.** `config.py:105` takes `SHOPCLOUD_URL` as-is. With `SHOPCLOUD_URL=http://127.0.0.1:9081` (a ShopCloud-like server outside the lab compose project), `authentication_abuse` sent 20 wrong-password logins and 1 real login to it. The outside server's log shows `20 "login_failed"`, `1 "login_success"`. The URL could just as well be any host. The run was `completed`, with no error and no warning. The README says "a script can never be pointed outside the lab". Fix: accept only a loopback URL whose port is the one published by the lab compose file, or check that the container behind it belongs to `cloudattacklab-lab`.
2. **The Grafana dashboard does not work.** `monitoring/grafana/provisioning/datasources/loki.yml` has `uid: PASTE_THE_UID_HERE`. `monitoring/grafana/dashboards/authentication.json` refers to the datasource as `fg492mjm656v4b` (a UID from someone's Grafana UI). Its one panel is titled "New panel". In Grafana: red error "Datasource fg492mjm656v4b was not found", "No data". Loki itself returned `25` for the panel's query at the same time.
3. **Cleanup and lab reset are not blocked while another run is active, and they break that run.** `scenario_engine/service.py:175` only checks that the run being cleaned is not active, and `LabManager.reset` checks no runs at all.
   - Cleanup of an old, already `cleaned_up` run during an `unauthorized_resource_access` run: the active run failed, "5 of 8 requests were not refused with 403" (its session was wiped), and no alert was raised.
   - Lab reset during `authentication_abuse`: ShopCloud was recreated mid-run, 5 requests errored, 14 of 15 failure events were stored, and the run still ended `completed`.
   - In the dashboard, the Cleanup button stays enabled on an old run.
4. **A run is reported `completed` when the evidence says otherwise.** The out-of-lab run had 0 events and `all_expected_met: false` in its report, and the reset-during-run case had `"errors": 5`. Both ended `completed` with `error: null`. The README says "no alert is raised from partial telemetry" for Loki, but with the Docker source a run with no telemetry still looks successful.
5. **Lab status is never checked against Docker.** After `pytest -m integration` stopped the lab, `GET /labs/{id}` and the Lab page showed `Status running`, with shopcloud, test_container and falco all `exited` and ShopCloud "unreachable". A WSL restart (which stops every container on this machine) leads to the same state.
6. **The dashboard shows false empty states while loading.** Every page first shows its empty state until the API answers:
   - Lab page: "No lab yet." with a "Create lab" button.
   - Scenarios page: "The lab is not running. Start it on the Lab page…" and "No scenarios.".
   - Alerts page: "No alerts yet.".
   - Incidents page: "No incidents yet."; the code (`IncidentsPage.jsx:68`) works the same way.
   All of these were seen in the browser; some were caught in screenshots.
7. **Events are tied to a run by time only** (`telemetry/ingest.py`: window starts at run start − 3 s, no end). Any request to ShopCloud in that window becomes the scenario's event. Seen in practice: the `lab_reset` record (`config_changed`) was stored as part of an `authentication_abuse` run. Nothing is made up, but someone browsing the shop during a demo run adds events to the scenario.
8. **Default credentials.**
   - Grafana has no `GF_SECURITY_ADMIN_PASSWORD`, so it runs with `admin/admin` and asks you to change it at first login.
   - `docker-compose.yml` falls back to the published `lab-dev-token` and `change-me-locally` when `.env` does not set them, which is the case for the current `.env`.
   All ports are bound to `127.0.0.1`, so this is low risk, but it contradicts `.env.example`'s "change the values".
9. **Incident lifecycle.** Incidents stay `open` after the response is verified and reverted. The risk score keeps its −20 "response verified as working" after the response was reverted (the auth incident still shows 40).
10. **The `stop_container` guard trusts Docker labels.** Any container labelled `cloudattacklab.role=test-target` and `com.docker.compose.project=cloudattacklab-lab` passes `check_test_container`. This needs Docker access to exploit, so it is a note, not a hole.

## README and docs claims I could not confirm (or found wrong)

- **`docs/api-contract.md`: "Status: planned. Nothing here is implemented yet."** This is wrong: every endpoint except `POST /auth/login` is implemented. `/auth/login` is listed for step 6 but does not exist (`openapi.json` has no `/auth` path).
- **README: "a script can never be pointed outside the lab"**: disproved (bug 1).
- **README, "What is here": `docker-compose.yml` is "Platform services (PostgreSQL for now)"**: out of date. It also runs the backend and the dashboard.
- **README, "monitoring/": Loki, Alloy and Grafana with a provisioned dashboard**: the stack starts and Loki works, but the dashboard does not (bug 2).
- **README: `cp .env.example .env` "then change the values"**:
  - It would overwrite an existing `.env`.
  - If you do change `LAB_CONTROL_TOKEN`, the README's later `python tools/check_shopcloud.py http://127.0.0.1:8081` (no `--lab-token`) uses the default `lab-dev-token` and fails 6 of 14 checks.
  - The README's by-hand `docker compose -f lab/docker-compose.lab.yml up` does not read the root `.env`, so it starts ShopCloud with the default token.
- **Falco through the dashboard** (`FALCO_ENABLED=true`, Lab page showing Falco healthy, Falco events on the alert): not confirmed in the UI, because that needs a `.env` change. Confirmed only by `test_container_scenario_with_falco_stop_container_and_cleanup`, which passed on this machine.
- **Loki failure behaviour** ("If Loki cannot be reached, the run fails before its script starts"; settle polling): not tested. The Loki happy path was confirmed: 21 events, all `loki:shopcloud:…`, 1 alert with 20 events.
- **"One active run per lab"**: not tested directly.
- **README "Build order"** still describes the plan ("Contracts and fake ShopCloud (this commit)"), not what exists.
- Confirmed as written: the risk scores 40 and 46; "2 of 7 follow-up logins were blocked with 429"; 8 of 8 refused and "Verification passed: access is still denied"; 20 and 8 linked events; 14/14 from `check_shopcloud.py`; the ShopCloud reset behaviour; and the no-secrets-in-logs claim.

## What would embarrass you in a live demo

1. **Opening Grafana.** First it asks you to change the `admin/admin` password. Then the only dashboard has one panel called "New panel" with a red error icon and "No data".
2. **Page loads.** The Lab page briefly says "No lab yet." with a "Create lab" button, and Scenarios briefly says "The lab is not running" and "No scenarios.". If someone clicks during that moment, or a screenshot catches it, it looks broken.
3. **Clicking Cleanup on the previous run, or Reset, while a scenario is running.** The live run fails or comes out short, and still may say `completed`.
4. **Pointing `SHOPCLOUD_URL` at another host.** If anyone asks "what stops this from attacking a real site?" and tries it, the run goes ahead and reports success.
5. **After a WSL restart, or after running the integration tests.** The Lab page says `running` with every container `exited`, and Run is refused with a pre-flight error.
6. **Showing `docs/api-contract.md`.** Its first line says nothing is implemented.
7. **Every source IP is `172.21.0.1`** (the Docker gateway), so "one source IP" in the alerts is always the same address. Worth explaining before someone asks.
